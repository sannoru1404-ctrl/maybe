# SubShare — этап 1: БД и Telegram authentication

Основа MVP, ещё не запущенная платформа. Next.js UI, API, эквайринг, бот и фоновые workers будут следующими этапами. Вложенное ТЗ использовано как справочный материал; требования пользователя имеют приоритет.

## Локальная проверка

Node.js 22+:

```sh
npm ci --cache /workspace/.npm-cache
npm run typecheck
npm test
```

Тесты выполняют SQL в PGlite (PostgreSQL WASM), не требуют Supabase, токена или сети. Проверяют применение миграции, последний слот, повторные события, начисление 85%, спор, права доступа и Telegram HMAC. PGlite выполняет запросы последовательно: настоящая конкуренция нескольких соединений ещё не проверена; транзакционные блокировки нужно дополнительно протестировать на серверном PostgreSQL.

## Supabase / PostgreSQL

Применить `supabase/migrations/202610070001_subshare.sql` через защищённое серверное соединение мигратора к PostgreSQL. Это одноразовая транзакционная миграция; повторное применение ведёт система миграций. Внешняя БД в этой среде не подключалась.

- `users.balance`, цена, суммы и комиссия — целые копейки RUB; округление комиссии до ближайшей копейки, остаток получает хост.
- `orders` фиксирует цену и хоста; invoice уникален в пределах провайдера, создание идемпотентно по `(buyer_id, idempotency_key)`.
- Каталог не содержит инвайтов, email или закрытых инструкций. Они находятся в `subshare_private`. RLS включён без клиентских политик; браузерным ролям ничего не выдано.
- Серверные функции работают с правами вызывающего (`SECURITY INVOKER`). Подключение backend должно иметь явно выданные права на схемы/таблицы/функции и серверный доступ, обходящий RLS. Не передавать это подключение браузеру и не добавлять эти схемы в Supabase exposed schemas.
- `activate_payment` вызывать только после проверки оплаты у провайдера: invoice, сумма, RUB и принадлежность заказу. Она блокирует заказ и затем лот; повторный webhook не уменьшает слот повторно. При опоздании оплаты или отсутствии слота создаёт `refund_requested` в outbox, оставляя заказ pending и payment_status refund_pending до подтверждённого возврата.
- `confirm_order` атомарно пишет ledger, баланс и completed. `p_timeout=true` разрешает завершение только по наступлению дедлайна. Worker получает buyer_id из БД; HTTP API никогда не принимает режим timeout от клиента.
- `open_dispute` разрешён покупателю до дедлайна, блокирует заказ и обнуляет таймер. Гонка с завершением сериализуется блокировкой заказа.
- `read_order_access` допускает только хоста/покупателя и только после escrow (включая completed/disputed). `p_actor` берётся из проверенной сессии.
- Outbox хранит идентификатор заказа и тип события; worker должен прочитать детали на сервере. Доставка сообщений и реальные возвраты ещё не реализованы. Статус refunded нельзя ставить при одном лишь запросе возврата.

Перед production нужны: API с Zod, проверенный адаптер провайдера и вебхуков, обработка отказа оплаты/подтверждения возврата, решения споров, таймер-worker, доставка outbox с retry/idempotency, интеграционные тесты конкурентных транзакций, секреты runtime и наблюдаемость. Схема поддерживает эти состояния, но не заменяет workers и эквайринг.

## Telegram

`src/server/auth/telegram.ts` экспортирует `validateTelegramInitData` и `authenticateTelegramRequest`. Заголовок: `Authorization: tma <raw initData>`.

Ключ Mini Apps: `HMAC-SHA256(key="WebAppData", data=BOT_TOKEN)`, затем HMAC от отсортированных декодированных полей без `hash`. Поле `signature`, если есть, входит в HMAC-проверку с токеном. Это отличается от Login Widget, использующего SHA-256 токена.

Сравнение подписи constant-time; запрещены дубликаты полей, неверный JSON/user, старые данные (1 час), даты более 30 секунд в будущем и payload >16 KiB. ID возвращается строкой для bigint БД. BOT_TOKEN остаётся только на сервере. initData является временным bearer credential: не логировать и передавать только по HTTPS. Авторизация не обеспечивает идемпотентность бизнес-операций; для неё предусмотрены ключи заказа и событий платежа.
